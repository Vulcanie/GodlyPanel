# Barotrauma - modded servers (STEP: mods, conventions section D)

Researched 2026-10-15. Game build: 1.13.4.0 (wiki banner "current game version is 1.13.4.0"; server csproj also says 1.13.4.0). Nothing was installed or run (read-only research). Raw copies of source files used are in `raw\` next to this file (`raw\src_*.cs`).
Evidence labels: **[SRC]** = the game's own public source, FakeFishGames/Barotrauma `master` (https://github.com/FakeFishGames/Barotrauma), **[WIKI]** = official wiki (the mods page is marked outdated, written for 0.18.12.0), **[LUACS]** = LuaCsForBarotrauma official docs/GitHub/Workshop page, **[HOST]** = hosting-company guides (weakest source, used only to cross-check), **[STEAM]** = Steam Workshop pages.

## 1. Verdict
Mods ARE supported on a dedicated server. There is no mod loader to install for ordinary mods: a mod is a folder with a `filelist.xml` ("content package"). The server loads the packages listed in `config_player.xml`. The server does NOT download or update Workshop items by itself, so GodlyPanel has to get the mod folders onto the server (copy, or SteamCMD) and write the list. Lua/C# scripting mods need one extra step: patch the server with LuaCsForBarotrauma.

## 2. How the server finds and enables mods [SRC]
- Two places a server looks for packages ([SRC] `raw\src_ContentPackage.cs` lines 31-35, `raw\src_ContentPackageManager.cs` lines 380-390):
  - `LocalMods` folder, relative to the server install folder (`LocalModsDir = "LocalMods"`). Each mod is a sub-folder containing `filelist.xml`.
  - The Workshop folder `%LocalAppData%\Daedalic Entertainment GmbH\Barotrauma\WorkshopMods\Installed` of the Windows user that runs the server (`WorkshopModsDir = Path.Combine(SaveUtil.DefaultSaveFolder, "WorkshopMods", "Installed")`, with `DefaultSaveFolder` = LocalApplicationData + "Daedalic Entertainment GmbH" + "Barotrauma"; comment in `raw\src_SaveUtil.cs` line 84 confirms the Windows path). Folders there are named by Workshop id.
- The list of enabled mods is `config_player.xml` in the server working folder (`GameSettings.PlayerConfigPath = "config_player.xml"`, `src\GameSettings.cs` line 531). The server sets its working directory to the exe folder (see 01-basics.md), so the file sits next to `DedicatedServer.exe`.
- If `config_player.xml` is missing, the game creates it with default config and saves it (`GameSettings.Init`: `currentConfig = Config.GetDefault(); SaveCurrentConfig();`, `src\GameSettings.cs` ~lines 580-583; the server calls `GameSettings.Init()` at `raw\src_server_GameMain.cs` line 85) [SRC]. So it exists after the first start; before that the panel may need to create it.
- Exact format the game itself WRITES (`src\GameSettings.cs` lines 675-686) and READS (`raw\src_ContentPackageManager.cs` lines 20-24 and 518-555):
  ```xml
  <contentpackages>
    <!--Vanilla-->
    <corepackage path="Content/ContentPackages/Vanilla.xml" />
    <regularpackages>
      <!--Mod display name-->
      <package path="LocalMods/ModFolder/filelist.xml" />
    </regularpackages>
  </contentpackages>
  ```
  (This sits under the root element of config_player.xml, next to other config sections. The element names are `contentpackages`, `corepackage`, `regularpackages`, `package`; the Vanilla path constant is `Content/ContentPackages/Vanilla.xml`.)
- Load rules [SRC] (`findPackage` in `ContentPackageManager.Init`): each `<package>` is matched first by `path` (case-insensitive compare, path cleaned to cross-platform form), and if none, by `name` attribute (`NameMatches`). A package that is not found is silently skipped (no error). There is no `enabled` attribute in the code: the game writes only `path`, and reads only `path`/`name`. (Some host guides show `enabled="true"`; it is ignored.) The ORDER of `<package>` lines is the load order (they are added in order and passed to `SetRegularEnumerable`), so put dependencies before the mods that need them.
- Because matching is by path against packages the game found in LocalMods or the WorkshopMods\Installed folder, the path for a Workshop-installed mod is what `CleanUpPathCrossPlatform` produces from its real location (for example a path under `...WorkshopMods/Installed/<id>/filelist.xml`). The exact string the game writes for such a path on a server was not observed (UNVERIFIED #3). Using LocalMods avoids the question.
- A mod can also be listed by `name="Mod Name"` (the `name` from its filelist.xml) instead of path [SRC], handy if the path is unknown; same fallback logic.
- Mods can only be changed while the server is stopped (packages are loaded at start in `ContentPackageManager.Init`). The `serversettings.xml` is a different file (settings are not the mod list). [SRC]

## 3. How the server gets Workshop mods
- The server does not subscribe to or update Workshop items: in the source `DeleteUnsubscribedMods` returns immediately on servers ("Servers do not run this because they can't subscribe to anything") and a compiler note says `#warning TODO: implement Workshop updates for servers at some point` (`raw\src_Workshop.cs` lines ~394-397; `raw\src_ContentPackageManager.cs` ~line 505) [SRC]. So: no auto download, no auto update on the dedicated server. Hosts confirm: "a dedicated server does not download Workshop mods automatically" (https://xgamingserver.com/blog/how-to-set-up-a-barotrauma-dedicated-server-and-install-mods/) [HOST].
- Official wiki procedure (outdated but not contradicted by source): subscribe on your own PC, start Barotrauma once so it downloads, copy the mod folders from `%LocalAppData%\Daedalic Entertainment GmbH\Barotrauma\WorkshopMods\Installed` (Linux `~/.local/share/Daedalic Entertainment GmbH/Barotrauma/WorkshopMods/Installed`) to the server, then list them in `config_player.xml`. https://barotraumagame.com/baro-wiki/index.php?curid=324 (raw copy `src\w_Enabling_Mods_on_a_Dedicated_Server.txt`) [WIKI].
- Same page, verbatim idea: "You can also acquire mods on the server side using SteamCMD, however the names of the folders SteamCMD downloads are incorrect and require manual renaming." No command is given [WIKI]. A hosting guide describes the SteamCMD result as `steamapps\workshop\content\602960\<id>` and says to rename to the mod's name and move into `LocalMods` (https://www.g-portal.com/wiki/en/?p=11786) [HOST]. Whether `workshop_download_item 602960 <id>` works with `+login anonymous` is UNVERIFIED #1 (app 602960 is the paid game; the dedicated-server tool 1026340 is free). Workshop id is the number at the end of the Workshop URL.
- Many hosts (e.g. https://www.gamehostbros.com/guides/games/barotrauma/install-mods, https://docs.emeraldhost.de/en/gameserver/barotrauma/add-mods) copy mods into `LocalMods/<Workshop id or name>/` and write `LocalMods/<name>/filelist.xml` lines [HOST]. This matches [SRC] (LocalMods is a package source). GameHostBros' panel also offers a "Workshop Mods" id box, but that is their panel feature, not a game feature [HOST]; how it fetches mods is UNVERIFIED.
- Submarine mods: the XGamingServer guide says submarine mods must be copied from the WorkshopMods folder too, not dropped into `Submarines/` (https://xgamingserver.com/docs/barotrauma/install-mods) [HOST].
- Dependencies: a mod's Workshop page lists "Required items"; the server does not resolve them, so each dependency must also be copied and listed first (host guides: GameHostBros above) [HOST]. The game itself has a "missing dependencies" check (`CheckMissingDependencies`, `raw\src_ContentPackageManager.cs` ~line 563) but it uses Steam UGC children and is a client-side warning [SRC, partly].

## 4. How players match the server [SRC unless noted]
- The server sends the list of its enabled packages to joining clients. In the client's `ModDownloadScreen` (`raw\src_ModDownloadScreen.cs`) missing mandatory packages are listed, and the player is offered (a) to download them FROM THE SERVER, when `AllowModDownloads` is true, or (b) a "Subscribe to all on Workshop" button (uses the Workshop id of each mod, `BulkDownloader.SubscribeToServerMods`) [SRC].
- Server setting `AllowModDownloads` (serversettings.xml attribute, default True, `src\ServerSettings.cs` lines 638-643): when true the server compresses every enabled non-Vanilla package that has multiplayer-synced content into `TempMods_Upload\*.barodir.gz` at start (`raw\src_ModSender.cs`), so players can fetch them from the server; with False players must use the Workshop. Official wiki text: "if disabled and if server/client has outdated mods ... players won't be able to join" and "If player chooses to download mods from the server, they will have to do it every time they join." https://barotraumagame.com/baro-wiki/index.php?title=Serversettings.xml (raw `raw\wiki_Serversettings.xml.txt` lines 245-251) [WIKI].
- `AllowFileTransfers` (default True) is a separate thing: only `.sub` files are transferred; a client missing a content package cannot connect at all (same wiki page, lines 253-259) [WIKI]. (Some hosts conflate the two; the wiki and source above separate them.)
- Mismatch rule: mods and versions must match the server's list or the client cannot join (host guides: https://xgamingserver.com/docs/barotrauma/install-mods; [SRC] hash is part of the package: `ContentPackage.Hash`) [HOST/SRC]. Download from the server sends the SERVER's copy, so a server with an old mod can force an old version on players; update server copies when authors update (no auto-update on servers).
- A server that sends its mods does so for packages with multiplayer-synced content only (`HasMultiplayerSyncedContent`, `ContentPackage.cs` line 158). Cosmetic/client-only content is not required to match (exact boundary UNVERIFIED #6).
- `ModsEnabled` is `true` whenever any non-Vanilla package with synced content is enabled; the server then shows as modded in the browser: `contentpackage0..9` keys plus a `packagecount` are published through Steam (max 10 listed) (`raw\src_server_SteamManager.cs`) [SRC].

## 5. Lua / C# scripting: LuaCsForBarotrauma ("Lua For Barotrauma", "LuaCs")
- What it is: a fork of the Barotrauma source adding Lua and C# modding, by Evil Factory. Source https://github.com/evilfactory/LuaCsForBarotrauma ; Lua docs https://evilfactory.github.io/LuaCsForBarotrauma/lua-docs/ ; Workshop item 2559634234 "LuaCsForBarotrauma", about 697,589 subscribers, last updated for v1.13.4.0, tags Client-side + Server-side, about 1,891 items depend on it (https://steamcommunity.com/sharedfiles/filedetails/?id=2559634234, read 2026-10-15; the page also shows a Steam notice that the item was "removed from the community" / "incompatible", meaning the Workshop package should not be relied on) [STEAM].
- Dedicated server install, official ("Installing LuaCs For Barotrauma Manually", read from `raw\luacs-manual.html`; https://evilfactory.github.io/LuaCsForBarotrauma/lua-docs/manual/installing-lua-for-barotrauma-manually/) [LUACS]:
  1. Download the right patch from https://github.com/evilfactory/LuaCsForBarotrauma/releases/tag/latest . The release `latest` ("Automatic build", published 2026-08-01) has assets `luacsforbarotrauma_patch_windows_server.zip` and `..._patch_windows_client.zip` (also linux/mac, and full `build_*` zips) (GitHub API, https://api.github.com/repos/evilfactory/LuaCsForBarotrauma/releases) [LUACS].
  2. The doc: the server patch "only affects the server files ... more useful for dedicated servers", and both patches "replace your server Vanilla executable" with the LuaCs one. Extract the files into the folder where the dedicated server is installed and accept replacing the .dll files.
  3. "Do NOT select the server executable after installing the patch ... You also don't need the content package at all anymore." So no launch flag and no config entry is needed on the server.
  4. Test: type `reloadluacs` in the server console (command missing means not installed).
- It must be re-applied after every server update, because a SteamCMD `app_update ... validate` restores the stock files (host guide wording: "reinstall after every game update or server reset", https://client.citadelservers.com/knowledgebase/1394/How-to-Install-the-LuaCs-Mod-on-Your-Barotrauma-Server.html [HOST]; the "validate" part is my inference from how SteamCMD works, UNVERIFIED #4). It also tracks the game version: a game update before LuaCs publishes a matching patch can break the server (inference, UNVERIFIED #5).
- Clients: players need LuaCs too for mods that use client-side Lua. Workshop page: classic method `install_cl_lua` in the console after hosting with the LuaCs server executable, or the GitHub auto-updater launch option, or the manual client patch (above) [STEAM/LUACS]. Server-only Lua mods work without the client patch (Workshop tags "Server-side"; exact per-mod behaviour UNVERIFIED #6).
- A hosting blog claimed a `-luaforserver` launch flag. NOT found in the official doc (which says no flag/selection is needed) and not in the game's server argument list (`03-launch-args.md`). Treat as wrong/UNVERIFIED #7.
- Windows/Linux note from a forum user: the Linux patch adds a launcher script; not relevant to GodlyPanel (Windows). UNVERIFIED.

## 7. Risks and gotchas
- No anti-cheat is involved in the source read (no EAC/BattlEye references in the server files used; absence not exhaustively searched, UNVERIFIED #9).
- Save compatibility: campaign saves made with mods contain mod content ids; removing a mod from the server later can break/corrupt a running campaign. The wiki/hosts do not state this firmly; hosts only warn that updates can make mods incompatible (https://client.citadelservers.com/knowledgebase/606/Barotrauma-Updated-Modding-Guide.html [HOST]). Treat as a warning, UNVERIFIED as a documented behaviour.
- After a GAME update, old mods can fail to load. In the Workshop-source path, a package that fails to load is DELETED from `WorkshopMods\Installed` ("Delete Workshop mods that fail to load to force a reinstall", `raw\src_ContentPackageManager.cs` ~lines 386-392) [SRC] - another reason to keep GodlyPanel's own copies in `LocalMods` rather than the Workshop folder.
- Wrong path or a missing mod folder is skipped silently (no error), so a typo yields a server that quietly runs without the mod; players then fail to match [SRC]. A host forum report of a startup error caused by the `language` setting in config_player.xml is anecdotal [HOST].
- First start after enabling mods: the server compresses all synced mods to `TempMods_Upload` (disk + a short delay) when `AllowModDownloads` is true [SRC].
- `config_player.xml` is rewritten by the game on config save (`SaveCurrentConfig` writes the whole file, `GameSettings.cs` ~line 732), so GodlyPanel should edit only the `<contentpackages>` block while the server is stopped, and keep everything else. [SRC]

## 8. Recommendation for GodlyPanel
1. Offer a `mods` field. Since the server cannot fetch Workshop items itself, the simplest honest feature: a list of Workshop ids (or folder names) that the panel treats as "installed in `LocalMods\<id>\`", and writes into `config_player.xml` as `<package path="LocalMods/<id>/filelist.xml" />` lines in list order, only while stopped. Provide a text area labelled "mods in load order" and a note that dependencies must come first.
2. Do not promise a one-click Workshop download unless SteamCMD anonymous download is proven (UNVERIFIED #1). Provide an "Add mod folder" step: copy a folder (zip) from the user's own Workshop download into `LocalMods`. If real-install testing shows `+login anonymous +workshop_download_item 602960 <id>` works, add a "download from Workshop id" button that copies `steamapps\workshop\content\602960\<id>` to `LocalMods\<id>`.
3. Show a short warning in the UI: players must have the same mod list and versions; mods update only when you re-add them; do not delete a mod used by a running campaign.
4. Offer an optional "Install Lua scripting (LuaCs)" action: download `luacsforbarotrauma_patch_windows_server.zip` from the GitHub `latest` release and extract over the install, with a reminder to repeat after a game update. No start flag. Mark as advanced; do not offer it by default.
5. Keep the setting `AllowModDownloads` visible in the settings catalog (default True) so friends can fetch mods from the server (note: they re-download each join).
6. Safe default: no mods, `config_player.xml` left to the game.
