# Terraria (tModLoader): implementation notes

Written 2026-10-17. Part 1 is a generic install capability; part 2 is the game module. Nothing was installed or started; no game server was run.

## Part 1: `zipInstall`, the install-from-GitHub capability

### What it is
A template may have `zipInstall: { repo: "<owner>/<name>", asset: "<file name>", maxBytes?, expect?: [file, ...] }` instead of an `updateAppId`. The create job then does this instead of the SteamCMD job (documented in the comment at the top of `src/server/data/gameTemplates.js`):

1. asks `https://api.github.com/repos/<repo>/releases/latest` for the newest release (a draft or pre-release is refused);
2. picks the asset by EXACT name (no prefix, pattern or case folding);
3. REQUIRES a SHA-256 from GitHub: the asset's `digest` field (`sha256:<64 hex>`). No digest, or one that is not sha256, means the install is refused before the file is requested; a download that does not match is deleted;
4. downloads over https only, from `github.com`, `objects.githubusercontent.com` or `release-assets.githubusercontent.com` (exact host names, no sub-domains, no credentials, no odd port), checked on the address in the release AND on where a redirect ends up; size must equal the size GitHub states and be within `maxBytes` (default 1 GiB; tModLoader 500 MB); 20 minute limit;
5. checks every name in the archive (`unsafeEntries`: absolute paths, drive letters, `..`) BEFORE unpacking anything, unpacks with the Windows `tar.exe` into the server's folder only, then refuses if a link was created and checks the `expect` files exist;
6. logs every step in the job log ("Asking GitHub ...", "Found v...", "Downloading ...", progress per 10 %, "SHA-256 matches", "Checking the names ...", "Unpacking N entries ...", "Installed ...");
7. needs consent: `createServer` answers HTTP 409 with `code: "zip-download-not-accepted"` and `details: { repo, asset, tag?, size?, sizeText? }` until the request carries `acceptZipDownload: true` (only a real `true` counts). The lookup that fills `details` reads release data only; if GitHub cannot be reached the question is still asked, without a size; if the release itself is unusable (no checksum, no such file...) the person gets an ordinary 400 instead of the question.

### Limits / not done
- No update path: a server installed this way has no `updateAppId`, so the panel's update button, auto-update and build tracker skip it (same as Minecraft modpack servers). Updating tModLoader means replacing files by hand (the guide says how).
- The zip is pinned to "latest" at creation time only; there is no version field (the dossier suggested one for pinning a working mod pack). Easy to add as a template field later.
- The Windows `tar.exe` is what unpacks (as for backups and the panel update); its handling of odd archives beyond the name check is not hardened further (links are rejected after the fact).
- GitHub's anonymous API limit is 60 requests an hour per address; two calls are made per creation (one for the question, one for the install).

## Part 2: the module

### Files
- `src/server/data/games/terraria.js`, `ui/src/catalog/games/terraria.js`, `tests/unit/game-terraria.test.js` (41 tests), `ui/src/__tests__/game-terraria.test.js` (24 tests). Not registered in either `index.js` (the lead does that).

### What it does
- `id/type terraria`, "Terraria (tModLoader)", `method: "process"`, no `updateAppId` (storeAppId 1281930 for artwork only), `zipInstall` from `tModLoader/tModLoader` asset `tModLoader.zip` (maxBytes 500 MB; expects `tModLoader.dll`, `start-tModLoaderServer.sh`, `LaunchUtils\busybox64.exe`, `LaunchUtils\ScriptCaller.sh`). Fields: sessionName (= world name), serverPassword, mods (Workshop ids or links).
- Port: ONE TCP game port, default **7878**. 7777 (the game's default) is Valheim's and Satisfactory's default here; 7778/7779 are kept by Valheim; nothing uses 7878 or 7879.
- Start script (`Start_Terraria.bat`):
  `start /MIN "<name>" "LaunchUtils\busybox64.exe" bash ./start-tModLoaderServer.sh -nosteam -config serverconfig.txt -port N -players N -tmlsavedirectory tmldata [-steamworkshopfolder steamapps/workshop]`
  (the last flag only when Workshop mods were asked for). Reasons:
  - the zip has NO `dotnet\` folder; the shipped script downloads .NET 8 on the first start. A script that started `dotnet\dotnet.exe` directly would fail the first time. So the panel runs the zip's own busybox + `start-tModLoaderServer.sh` (which is what the shipped `.bat` does, minus its `start`/return-at-once wrapper), which also runs `QuickEditDisable.exe` (a click in the console would otherwise freeze the server);
  - `-nosteam` is mandatory: without `-steam`/`-nosteam` the shipped script waits for a typed answer;
  - the shipped `.sh` does `launch_args="$launch_args $1"` and then `./ScriptCaller.sh $launch_args` UNQUOTED, so any value with a space is split into two arguments. Therefore every value on the launch line is one word (relative folder `tmldata`, numbers), and everything that can have a space (the world's full path, its name, the password) is in `serverconfig.txt`. The Launch options catalog says so, and a test pins it.
- `processName: "dotnet.exe"`, tracked by path: `<install>\dotnet\dotnet.exe` is inside the server's folder, so `serverProcesses.classify` owns it and not any other .NET program (tested with sibling-folder and `C:\Program Files\dotnet` cases, Windows only). Until the first start has downloaded .NET there is no `dotnet.exe`, so the panel shows the server as stopped during that time; the crash watcher only judges a server it has seen online, so no restart loop. Nothing kills by image name. Window mode `minimized` (not hidden) so the console can be reached.
- `serverconfig.txt` (written by the panel, replaces the all-commented example): `world=<install>\tmldata\Worlds\<name>.wld` (no quotes), `autocreate=2`, `worldname=<name>`, `password=<pw>` when set. Port and player limit are NOT written to it (they are on the launch line, which is where the panel's port editor changes them: two copies could disagree). Format fit: the shipped file is `key=value` with `#` comment lines, which is exactly the panel's **properties** parser (value = everything after the first `=`, so a password with `=` or `#` survives; edits replace the value on its line only; keys that are not in the file yet are offered). So the Settings tab edits it with the properties parser; the convar parser was not needed. One cosmetic point: the properties writer re-joins lines with `\n`, which the game reads fine.
- Data kept inside the server's folder with `-tmlsavedirectory tmldata` (relative): `tmldata\Worlds`, `tmldata\Mods`, `tmldata\ModConfigs`. Backup: Worlds, ModConfigs, Mods, serverconfig.txt, banlist.txt (Workshop downloads in `steamapps` are left out). Logs: dir `tModLoader-Logs` (server.log, Launch.log, Natives.log).
- Config catalog (26 settings, `root::<key>`): world, autocreate, worldname, seed, difficulty, password, motd, secure, language, banlist, upnp, npcstream, priority, modpath, modpack and 11 `journeypermission_*`. Left out: `port`, `maxplayers` (launch line); `worldrollbackstokeep` (key spelling unknown, the wiki writes `WorldRollbacksToKeep`; the launch argument of the same name is offered); 4 Journey keys whose meaning rests on the key name alone (`increaseplacementrange`, `setdifficulty`, `biomespread_setfrozen`, `setspawnrate`).
- Launch arguments (17): -nosteam, -config, -tmlsavedirectory (managed, not editable), -port, -players (managed), -ip, -noupnp, -secure, -banlist, -worldrollbackstokeep, -language, -disableannouncementbox, -announcementboxrange, -modpack, -modpath (not editable), -steamworkshopfolder, -savedirectory (not editable). Left out on purpose: -world/-worldname/-autocreate/-seed/-pass (config file; spaces), -steam/-lobby/-friendsoffriends (no Steam lobby), -forcepriority (accepted forms unverified), -server (the script adds it), all mod-author/client flags.
- Mods (dossier section 10 recommendation, implemented with the existing SteamCMD plumbing, like Squad/L4D2): the `mods` field takes Workshop ids or links. In `postWrite`, for each id, anonymous `steamcmd +force_install_dir <install> +login anonymous +workshop_download_item 1281930 <id> +quit` (one call per id, 90 min limit), then every `.tmod` found under `steamapps\workshop\content\1281930\<id>` is read for its INTERNAL name (header layout from `TmodFile.Read`: `TMOD`, tML version string, 20-byte hash, 256-byte signature, int32, then the name as a BinaryWriter string; name must look like a C# identifier) and `tmldata\Mods\enabled.json` (a JSON array of internal names, what `ModOrganizer.LoadEnabledMods` reads) is written. Downloads stay in `steamapps\workshop` (tModLoader scans it through `-steamworkshopfolder steamapps/workshop`). A failed id, an unreadable name, and the dependency problem (SteamCMD does not fetch a mod's "required items") are reported as job warnings. SteamCMD itself (with the usual consent) is only needed when mods are asked for (`needsSteamCmd`).
- Graceful stop: **impossible from the panel** (the `exit` console command needs stdin). Said in: the template description (capitals), the first creation warning, the guide's first note, the header comment, the entry's `windowMode: "minimized"`. `exit-nosave` is warned against.

### Deviations from the dossier / decisions to review
- The brief and dossier name `dotnet\dotnet.exe tModLoader.dll` as the process; I track that process but START it through busybox + the shipped script (reason above). If a real install shows the direct form works after the first start, a `if exist` branch could be added, at the price of losing `QuickEditDisable`.
- Default port 7878, not 7777 (clash with Valheim/Satisfactory defaults).
- `-players` (not `-maxplayers`) on the line; default 8 (the shipped example; the Terraria wiki says 16, sources disagree, so it is always written).
- `difficulty` dropdown offers 0-3 (Terraria wiki); the shipped tML example comment lists only 0-1. Described as expected-to-work, untested.
- `secure`/`upnp` offer `1` On and `0` Off; the example files only show 1 (0 as off is inferred). Stated in the descriptions.
- Journey permission rows are described from key names plus the wiki's 0/1/2 meaning; flagged "not tested whether tModLoader honours them".
- `autocreate=2` (Medium) is always written; `difficulty` and `seed` are not (no default is documented; the person can add them in the Settings tab).
- No evil-biome control: no key or flag exists in any source.

### Needs a real install to verify
1. The whole create job on the real GitHub: the lookup, `digest`, size and redirect host were checked read-only (see Tests); still to be seen are the actual 61 MB download, the Windows tar unpacking of it and that the `expect` files are all present.
2. `start /MIN ... LaunchUtils\busybox64.exe bash ./start-tModLoaderServer.sh ...` from a panel-started (hidden PowerShell Start-Process) launch: that the chain reaches `tModLoader.dll`, that no question is asked, that the first start downloads .NET 8 unattended (needs internet) and that `<install>\dotnet\dotnet.exe` is then the running process (the panel's online/stop detection depends on it). If busybox stays as the parent, check Stop kills the tree.
3. That relative `-tmlsavedirectory tmldata` and `-config serverconfig.txt` work from the install folder (cwd), that Worlds/Mods are created, and that `world=<absolute path with spaces>` and `autocreate=2` create the world with no console question (the outdated wiki page says a missing world prompts).
4. That `-port` and `-players` on the line are honoured with a config file that has no `port=`/`maxplayers=` (the config says some settings are ignored unless a world is specified: one is).
5. Stop behaviour: what closing the window / ending the process does to the world; how often it autosaves; whether `exit` typed in the minimized window works (stdin shared by busybox and dotnet).
6. Workshop: SteamCMD anonymous `workshop_download_item 1281930 <id>` really downloads; the folder layout inside an item (`<id>\2026.8\*.tmod` expected); that tModLoader loads it through `-steamworkshopfolder steamapps/workshop` (relative); that `enabled.json` with the read names enables the mods; `.tmod` name parsing against a real mod file.
7. Join test with a tModLoader client; firewall prompt for `dotnet.exe`; TCP port reachable.
8. Whether tModLoader honours the `journeypermission_*` lines, `secure=0`, `upnp=0`, `difficulty` 2 and 3.
9. The registered module in the panel: the dashboard artwork for storeAppId 1281930, the Logs tab for `tModLoader-Logs`, backup and restore of `tmldata`.
